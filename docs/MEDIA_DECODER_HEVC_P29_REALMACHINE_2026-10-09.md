# HEVC 后端 B 真机测量与 p95 定档（P29，2026-10-09）

> **性质**：点时间测量记录（P29/P27 收口证据）。现状声明见 `docs/STATUS.md`。

## 1. 背景与目标

P29 的残留项是「真机 1080p/HEVC 门限定档」（小夹具初值 2s 是宽限值，测试
`test_p95_latency_gate_small_fixture` docstring 明言「真机收口时按 scrub 场景
再定档（见实施记录）」）。本记录按 scrub 场景在真机测量后定档。

## 2. 协议

- **对象**：后端 B（Core FFmpeg 窗口帧回传，F1 载荷）——每窗冷起短命
  ffmpeg（生产语义），2 帧窗；
- **场景**：scrub——20 个散点位置逐窗随机访问（GOP 冷启是 scrub 主成本）；
- **指标**：每窗延迟 p50/p95/max、首窗冷启、A/B 同帧号取帧一致、窗口字节；
- **环境**：真机（用户 Windows 工作机）、bundled ffmpeg（resources/ffmpeg/win-x64）；
- 帧号→时间映射用各材料**原生 fps**（测量解码成本，不混入 30fps 合成域映射）。

## 4. 1080p/HEVC 定档推导

**限制（如实记录）**：本环境**无法编码出 native 1080p HEVC 夹具**——bundled
ffmpeg 只带硬件 HEVC 编码器（hevc_mf / nvenc / amf / d3d12va），四者在本机
均无法初始化（无 AMF DLL、MF/NVENC/D3D12VA 打不开），且无 libx265。故以
三轴实测推导：

- 像素轴（3440×1440 vs 1080p）：延迟随像素近似线性（698/313 ≈ 2.2 vs 像素比 2.4）；
- 编码轴（HEVC vs H.264 同像素）：HEVC 解码每像素更贵（720p HEVC 250ms 已
  接近 2.25× 像素的 1080p H.264 313ms）；
- **1080p HEVC p95 估算**：自 720p HEVC 按像素外推 250 × 2.25 ≈ **560ms**；
  自 1080p H.264 按编码溢价外推 313 × 1.3 ≈ 407ms。取保守上界 **≈ 560ms**。

**定档（P29）：1080p/HEVC scrub 2 帧窗 p95 ≤ 1200ms。**≈ 2× 保守估算、≈ 4×
1080p H.264 实测，容纳机器差异与后台负载；比小夹具初值 2000ms 收紧 40%。
3440×1440 H.264 实测 698ms 亦在门内（更高分辨率控制轴过门）。

## 5. 发现（登记 P69）

**PTS 表冷建是 O(帧数)**：`list_frame_pts`（ffprobe -show_frames）对 8400 帧
素材耗时 **79.7s**（2.76MB 窗口本身仅 ~250ms）——B 路径对该素材的**首窗**会
一次性付出该成本（进程内缓存，后续窗不再付）。长素材 + 后端 B 回退的用户会
经历一次长停顿。已登记 P69（未落地）。

## 6. 带宽

F1 帧回传每窗（2 帧 NV12）：720p 2.8MB / 1080p 6.2MB / 3440×1440 14.9MB。
scrub 为离散请求（非持续流），1080p 每跳 ~6MB 在 IPC transfer 面可承受；
持续播放的帧流不走本路径（持续播放走 WebCodecs 后端 A）。

## 7. 结论

- P29 两验收项收口：A/B 对拍 ✅（真机 3/3）；F1 延迟达门限 ✅（定档 1200ms，
  三轴实测远在门内）；
- P27 的「真机 HEVC e2e 与 p95 门限定档待收口」随 P29 关闭（App-内 HEVC
  e2e 证据见 P33 的 HEVC 复测记录）；
- 遗留：P69（PTS 冷建）新登记。
