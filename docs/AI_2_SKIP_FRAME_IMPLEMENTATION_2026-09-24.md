## 0. 问题与根因

`AI_VALIDATION_REPORT_2026-09-20.md` 实验 A 记载：dance（1080p50）分析墙钟
**19.5s/分钟源**，超性能门（≤10s）一倍。拆解实验确认根因为
**`select` 滤镜之前的全量解码**——FFmpeg 必须先解码一帧才能求值 `pict_type`，
50fps×1080p 的解码成本乘积与实测墙钟吻合。**与采样点数、与 CV 技术路线无关。**

已实测的修复方向：`-skip_frame nokey`（解码器只解 I 帧）在 dance 上 6.4 倍加速
（22.3s→3.5s）且输出逐字节一致。**代价**：长 GOP 素材的"≥1s 兜底采样"在
`skip_frame` 下失效——兜底依赖解码非 I 帧的时间戳，而 skip_frame 下这些帧不可见
（lichun 167 帧→30 帧）。8s 空洞内的快速运动因此不可见。

## 1. 裁决（见规划门 §1）

裁决全文见 `CV_SKIP_FRAME_PLANNING_GATE_2026-09-20.md` §1。采用**混合自适应**，非二选一：

- **默认快路径**：`-skip_frame nokey` + `select` 退化为纯 `eq(pict_type,I)`；
- **长 GOP 自动回退**：快路径采样点**最大间隔** > `CV_SAMPLE_GAP_FALLBACK_US`（4s）
  判定长 GOP 素材 → 全量解码重跑（`select` 恢复"I 帧 或 距上帧 ≥1s"兜底），
  消除空洞盲区；
- 4s 阈值取"采样密度与重跑成本"的折中（实测 lichun 最大 GOP 8.33s 触发回退；
  dance 全 1.0s GOP 不触发）。

规划门同时**否决**了"纯 skip_frame 不回退"（8s 盲区）与"维持全量解码"（性能门持续超标）。

### 1.1 规划门提出但**未交付**的一项（本文新增发现）

规划门对阈值参数有两处"可配"要求：

- §1.2：「间隔 > 4s（**GAP_THRESHOLD，可配**）」；
- §4 风险表：「稀疏检测阈值 4s 对特定素材不合适 | 对策：**可配常量**」。

现状：`CV_SAMPLE_GAP_FALLBACK_US` 与 `MIN_SAMPLE_INTERVAL` **均为模块常量，无任何可配入口**。
即规划门的"可配"要求未落地。这与本文 §4.3 的"采样密度参数未暴露"是同一件事的
两个来源——**不是 ADR-0004 D6 新提出的需求，而是规划门既有要求的历史欠账**。

### 1.2 与 ADR-0004 D6 的关系（口径变化）

规划门 §1 否决方案第三条：「密度参数用户可调：普通用户无判断依据，**搁置（性能门测量后再议）**」。

ADR-0004 D6（2026-09-24）改为「默认自适应 **+ 高级用户可调**」，即解除了该搁置。
**口径变化的依据**：性能门测量已完成（本文 §3），"再议"的前置条件已满足；
且规划门 §1.2/§4 本就有"可配"要求，D6 是把"内部可配"推进到"用户可调"。
**执行以 ADR-0004 D6 为准。**

## 2. 实现

| 面 | 内容 |
|---|---|
| `cv_video_args` | 双路径：`skip_frame=True`（快路径，`-skip_frame nokey` + 纯 I 帧 select）/ `False`（全量路径，保留 ≥1s 兜底）。另有 `fallback_interval` 开关（测试用） |
| `run_analysis_job` | 混合自适应编排：默认快路径 → 计算相邻采样点最大间隔 → 超阈则全量回退重跑 |
| 人脸通道 | 同步 `skip_frame`（RGB 遍历与灰度遍历**帧序对齐保持**）；**并修复 `analyze_faces` args 替换未生效的残留**——视频遍历快路径已生效而人脸通道未生效，即 25s 差异的来源 |
| `CV_ALGORITHM_VERSION` | 1 → 2（信号集语义未变，但采样策略变化需版本隔离；旧行标记 stale，不原地重算） |

## 3. 性能证据（2026-09-24 独立复测）

工具：`tools/validation/measure_cv_sampling.py`（**直接 import 生产代码
`cv_video_args`**，不复制 FFmpeg 参数，保证测的就是产品实际执行的命令）。
原始数据：`evidence/cv_sampling/20260924T042636Z.json`（algorithm_version = 2）。

### 3.1 复测结果

| 素材 | 时长 | 最大 GOP | 快路径 | 全量路径 | 加速 | 回退 | 有效 s/分 | 门 |
|---|---|---|---|---|---|---|---|---|
| dance (1080p50) | 168.0s | 1.00s | 3.3s / 168 帧 | 19.5s / 168 帧 | **6.0x** | 否 | **1.2** | ✓ |
| science (720p) | 10.1s | 7.08s | 0.1s / 2 帧 | 0.2s / 11 帧 | 2.0x | **是** | **1.8** | ✓ |
| lichun (720p) | 150.9s | 8.33s | 0.3s / 30 帧 | 2.7s / 167 帧 | **8.8x** | **是** | **1.2** | ✓ |

摘要：`all_meet_gate = true`，`max_effective_per_minute_s = 1.8`（门 10.0）。

### 3.2 复测的三个发现（原实施未记录）

1. **回退的双遍遍历成本可忽略**——代码走读时曾担心"长 GOP 素材白跑一遍快路径"。
   实测反驳：lichun 快路径 0.3s + 全量 2.7s = 3.0s，相对直接全量 2.7s
   **仅 11% 开销**；science 同量级（0.1s+0.2s）。**不需要为此优化。**
2. **快路径的"逐字节一致"仅在非回退素材上成立**——dance 快/全两路均 168 帧，
   确认逐字节一致；但 science（2 vs 11 帧）与 lichun（30 vs 167 帧）**帧数不同**，
   这正是回退机制存在的意义。原表述"输出逐字节一致"若不限定条件会误导。
3. **本测量为"视频采样分量"，不是完整作业墙钟**——dance 采样 1.2s/分，而 commit
   `a349866` 记录的**完整作业**为 4.3s/分，差额（约 3.1s/分）来自音频能量遍历、
   YuNet 人脸推理与 Python 侧信号计算。**性能门以完整作业为准**，本节分量数据
   的用途是定位剩余预算去向——优化后视频采样已不再是 dance 的瓶颈。

### 3.3 完整作业数据（来源：commit `a349866`，2026-09-21）

dance 1080p50 **21.5 → 4.3s/分**；science 8.5 → 7.6s/分；lichun 5.1 → 3.4s/分
（触发回退两遍遍历仍达标）。三素材全部 ≤10s/分。

信号一致性（与旧基线逐值比对）：dance 0 切点 / lichun 19 切点 / 24 人脸帧**不变**。
回归：Core 868 passed + 2 skipped。

## 4. 剩余范围（W0.2 修正后）

### 4.1 ⚠️ 完整作业复测受阻：`run_validation.py` 挂起（新发现，需处置）

本次尝试用 `tools/validation/run_validation.py --skip-bc` 复跑完整作业，**该脚本挂起**：
进程存活 13 分钟无进展，CPU 接近空闲，无 `ffmpeg`/`ffprobe` 子进程，
`.validation/app.db` 仅在启动后 2 秒被写过一次。

已排除：`start_core()` 有 60s 硬超时并抛 `RuntimeError`（未抛，说明 sidecar 正常起来，
且 `try` 块在 `start_core` 之后），故卡点在**实验 A 流程内部**。

**影响**：该脚本是仓库唯一的"真素材 + 真 sidecar"验证驱动，也是总纲 §11 评测体系
与 W0.4 的候选基座。挂起即意味着**当前无法复跑任何真实链路验证**。
建议**单独立项处置**（本工作单不含），且在 W0.4 选型评测 harness 基座前必须先解决。

### 4.2 4K60 档未标定

规划门定义两档性能门（1080p30 / 4K60），**4K60 从未测量**，
`test-assets/` 无 4K60 素材。测量脚本已支持 `--asset` 参数，素材到位即可补测：
```
.venv\Scripts\python.exe tools/validation/measure_cv_sampling.py --asset <4K60路径> --label 4k60
```

### 4.3 采样密度参数未暴露（**规划门既有欠账** + ADR-0004 D6）

现状：`MIN_SAMPLE_INTERVAL = 1.0` 与 `CV_SAMPLE_GAP_FALLBACK_US = 4_000_000`
均为模块常量；`CvAnalysisRequest` 仅 `generate: bool`（`extra="forbid"`），
注释明示"参数服务端固定"。

**双重来源**：规划门 §1.2/§4 早已要求阈值"可配"（见本文 §1.1）；ADR-0004 D6 进一步
要求"高级用户可调"。前者是历史欠账，后者是口径推进。

**机制待裁决**：(a) API 可选参数；(b) Desktop 设置项；(c) 二者（API 为底层、设置项为入口）。
三者对契约与回归面的影响不同，**不自行决定**。

### 4.4 规划门验收 §1/§2 的自动化回归锁缺失

见本文 §5 核对表。两项验收（sha256 对拍锁、合成长 GOP 回退触发用例）为人工实测，
无自动化测试。**建议在 W1.2 触碰 `run_analysis_job` 之前补齐。**

## 5. 规划门验收项落实核对（2026-09-24 复核）

规划门 §3 列了 5 项验收。逐项核对结果：

| # | 规划门验收项 | 落实 | 证据 |
|---|---|---|---|
| 1 | 对拍回归：纯 I 帧素材快路径输出与旧路径**逐字节一致（sha256 锁）** | ⚠️ **实测过，但无自动化锁** | commit `a349866` 记载已对拍；本次复测 dance 快/全两路均 168 帧。但 `test_cv_signals.py` 中**无 sha256 对拍用例** |
| 2 | 回退正确性：**合成长 GOP 素材**触发回退、兜底采样恢复、无 >4s 空洞 | ⚠️ **无自动化测试** | `test_cv_signals.py` 19 个用例中无回退触发用例；`a349866` 对测试的改动仅涉及 `algorithm_version` 行语义 |
| 3 | 性能门：三素材 ≤10s/分 | ✅ | 完整作业 4.3/7.6/3.4；分量复测 §3.1 |
| 4 | 召回层回归：场景段数量/排序与阶段三基线一致 | ✅ | commit 记载 dance 0 切点 / lichun 19 切点 / 24 人脸帧不变 |
| 5 | Core 全量 + `algorithm_version` 升级后旧行 stale 语义正确 | ✅ | 868 passed + 2 skipped；测试已适配 v1 行保留语义 |

**发现：验收 §1/§2 是"人工实测过、但没有回归锁"。** 规划门明确要求的是
`sha256 锁`与`合成长 GOP fixture 的回退触发测试`，即**自动化回归**，
而交付的是人工对拍记录。二者不等价：

- 无 sha256 锁 → 后续任何改动若破坏"非回退素材双路径一致"，无人会发现；
- 无回退触发用例 → 阈值或检测逻辑改坏（如阈值误改、`max_gap` 计算错），无人会发现。

**影响面**：W1.2（节拍分析）将并入同一 `cv_analysis` job 的音频通道，必然触碰
`run_analysis_job` 编排；**在动它之前应先补这两个测试**，否则等于在无护栏的
路径上叠加改动。

**建议**：作为 W0.2 的剩余项之一（第 5 项）——补两个单测：合成 fixture 的回退触发
用例 + 非回退素材的双路径 sha256 对拍用例。

## 6. 结论

- **性能门 1080p 档已达标**（完整作业 4.3/7.6/3.4 s/分，全部 ≤10）；分量复测自洽。
- **规划门存在且质量完整**；缺的是实施记录与 evidence（本文补齐），
  以及验收 §1/§2 的自动化回归锁（未补齐）。
- W0.2 的 **CV 前置对 Wave 1 已实际解除**——节拍分析（W1.2）与语义索引（W3.1）
  可基于当前采样引擎开展，**但 W1.2 动 `run_analysis_job` 前应先补回退/对拍测试**。
- 剩余四项：4K60 标定（待素材）、参数暴露（待机制裁决，**且为规划门既有欠账**）、
  验收 §1/§2 回归锁（建议先补）、验证 harness 挂起（**建议单独立项，优先级高于 W0.4**）。
