# CV 采样预算与诚实降级（ADR-0005 阶段 1）——Planning Gate

> 起草：LiuWei（架构师），2026-09-24。承接 `docs/design/adr/0005-cv-sampling-density-policy.md`
> 阶段 1（成本模型 + 诚实降级）。实施：ZhangSan（Core）；验收：LiuKeAi。
> 分支建议：`ai/cv-sampling-budget`。

## 0. 现状走读结论（2026-09-24 代码级）

### 0.1 当前编排（`media/cv_signals.py` `run_analysis_job`）

1. 快路径 `analyze_video(skip_frame=True)`；
2. 计算相邻采样点**最大间隔** `max_gap_us`；
3. `max_gap_us > CV_SAMPLE_GAP_FALLBACK_US`（4s）→ **无条件**全量解码重跑；
4. 音频遍历 → 人脸通道 → 落库。

**问题在第 3 步：没有任何成本判断。** 4K60 长 GOP 素材因此付出完整作业
**40.5 s/分钟源**（门 ≤10）——超门 4.1 倍，且**用户与召回层都无从知晓**。

### 0.2 存储现状（迁移 v21）

`cv_analyses` 列为：`id / asset_id / source_fingerprint / algorithm_version / status /
model_revision / sample_count / scene_cut_count / created_at / updated_at / finished_at`。

**无任何密度字段**——"这次分析达到了什么采样密度"当前**不可查询**，
只能靠扫 `cv_samples` 反推最大间隔。

### 0.3 作业预算机制现状

`job_scheduler.KIND_POLICIES` 仅有资源类型与优先级（`cv_analysis` = `light`×1、优先级 3）。
**全仓库无作业级墙钟预算/deadline 机制**（唯一近似物是渲染域的 `RENDER_VALIDATION_TIMEOUT`，
场景专用）。本单需自建。

### 0.4 两个影响设计可行性的发现（本单新查）

1. **`analyze_video` 不可中途中断。** 其 `cancel_event` 只在读循环**结束后**检查
   （`cv_signals.py:465`），循环体内无检查、无进程终止路径。
   → 若要做"回退超时即中止"，**必须先让该函数支持中途取消**（本单范围，见 §1.3）。
2. **`analyze_video` 的 `progress` 参数被接受但从未使用。**
   函数体内无任何 `progress` 调用——视频遍历阶段的细粒度进度实际未上报。
   → 属既有小缺陷，本单**顺带修复或显式登记**（见 §5 开放问题）。

### 0.5 4K60 实测基线（`AI_2_SKIP_FRAME_IMPLEMENTATION_2026-09-24.md` §4.2）

| 素材 | 完整作业 s/分 | 门 |
|---|---|---|
| 4K60 H.264 GOP 1s | 5.4 | ✅（余量仅 1.85 倍） |
| 4K60 HEVC GOP 5s | **40.5** | ❌ 超门 4.1 倍 |
| 1080p50 H.264（dance） | 4.7–5.4 | ✅ |
| 720p H.264 长 GOP（lichun） | 3.6–3.7 | ✅ |

**关键对比**：同为"长 GOP 触发回退"，1080p 的 lichun 仅 3.6 s/分，4K60 HEVC 却 40.5 s/分。
**同样的决策在不同分辨率下代价差 11 倍**——这正是"无条件回退"的失效点。

## 1. 范围

### 1.1 必须实现

1. **`cv_analysis` 墙钟预算**：`budget_s = duration_min × PER_MINUTE_BUDGET_S`，
   默认 `PER_MINUTE_BUDGET_S = 10`（对齐性能门），下限 15s、上限 300s。
   常量集中定义，为 ADR-0005 阶段 2 的"可配"留出接入点。
2. **回退准入判断**：快路径结束后，用**保守静态估算**判断全量回退是否可能超预算；
   可能超 → **不回退**，保留快路径采样。
3. **回退硬 deadline（双保险）**：即使准入通过，回退仍带 `deadline = 剩余预算`；
   超时则中止回退、保留快路径采样。**需先让 `analyze_video` 支持中途取消。**
4. **迁移 v23**：`cv_analyses` 增 `density_status`（`full` / `sparse`）、
   `gap_threshold_us`（分析时阈值快照）、`achieved_max_gap_us`、`wall_clock_ms`。
   存量行回填 `full`（依据见 §2.5，需在迁移测试中断言）。
5. **召回层消费**：`_cv_scenes` 排序对 `sparse` 分析降权（权重值以测试钉死）。
6. **契约暴露**：`POST …/cv-analysis` 响应 DTO 增 `density_status` 等字段（**增量可选**）。
7. **估算模型标定数据入档**：模型常量、标定来源、已知误差方向写入实施记录。

### 1.2 明确不做（边界）

- **连续密度旋钮**（ADR-0005 阶段 2）——本单只做"回退 / 不回退"的二值 + 诚实标记。
- **硬件解码**（阶段 3）。
- **Desktop 专用 UI 徽标**——字段先落地，界面为后续小单（与 CV 分析入口的先后关系同例）。
- **定点补洞**——ADR-0005 D4 已实测否决，不得重新引入。
- **修改 `MIN_SAMPLE_INTERVAL` / `CV_SAMPLE_GAP_FALLBACK_US` 的默认值**——
  本单改变的是"超阈后怎么办"，不是"阈值取多少"。
- **改写 `algorithm_version` 语义**——本单不改变信号计算，故**是否递增见 §5 开放问题**。

### 1.3 `analyze_video` 中途取消（本单必要前置）

- 读循环内**周期性**检查取消事件（建议每 N 帧或每 X ms，实施时定值）；
- 置位后**终止子进程**（`process.kill()` + `await process.wait()`），不留孤儿；
- 抛既有 `CvAnalysisError("JOB_CANCELLED")`，语义不变（调用方据此区分）。

## 2. 设计要点

### 2.1 预算公式

```
budget_s = clamp(duration_min × PER_MINUTE_BUDGET_S, FLOOR_S=15, CAP_S=300)
```

下限 15s 的理由：极短素材（如 10s）按比例只有 1.7s，连快路径都不够，
会把正常素材误判为超预算。上限 300s 的理由：防止超长素材（1 小时）获得
600s 预算而长时间占用 `light` 令牌（`cv_analysis` 与 waveform 共享）。

### 2.2 保守静态估算模型

```
projected_full_decode_s = duration_s × (width × height × fps) / THROUGHPUT_PX_PER_S[codec]
```

| 编码族 | `THROUGHPUT_PX_PER_S` | 标定来源 |
|---|---|---|
| h264 | 894e6 | dance 实测（1080p50 真实素材，全量 19.5s / 17.42 Gpx） |
| hevc | 331e6 | 4K60 合成素材实测 H.264:HEVC = 1:2.7，按比例折算 |
| 其他/未知 | 331e6 | **取保守值**（宁可高估成本、少回退） |

**已知误差方向：偏保守（高估成本）。** 实测 4K60 合成素材上该模型高估约 **2.4 倍**
（模型 33.4 s/分 vs 实测 13.9 s/分）——因合成内容比真实素材更易解码。
**误差方向是安全的**（高估 → 更倾向不回退 → 更省时），但会**误伤**
本可承受的素材。故必须有 §2.3 的 deadline 兜底，且模型须随实测持续校准。

### 2.3 双保险（估算 + deadline）

估算模型误差已知可达 2.4 倍，**不足以作为唯一保证**。因此：

1. 估算说"可能超预算" → 直接不回退（省时）；
2. 估算说"可承受" → 仍带 `deadline = 剩余预算` 执行回退，超时中止。

**这样最坏情况的浪费被 deadline 界定**，而估算负责避免不必要的尝试。

### 2.4 中止语义（必须与用户取消区分）

- 回退使用**自己的** `asyncio.Event`（`fallback_cancel`），不复用作业的 `cancel_event`；
- 两者都要检查：作业 `cancel_event` 置位 → 整个作业取消（既有语义不变）；
  `fallback_cancel` 置位 → **只丢弃回退结果**，用快路径采样继续；
- 判定顺序：先查作业取消，再查回退中止——避免把用户取消误判为"回退中止"而错误地
  产出一份 sparse 结果。

### 2.5 `density_status` 语义

**判据是"回退阈值"，不是"目标间隔"。**（初稿误用 `MIN_SAMPLE_INTERVAL` = 1s 作判据，
会把 1s < 间隔 ≤ 4s 这一正常区间的素材大量误标为 sparse——该区间本就不该回退。）

| 值 | 含义 |
|---|---|
| `full` | `achieved_max_gap_us ≤ gap_threshold_us`——**没有留下"本该填而没填"的盲区** |
| `sparse` | `achieved_max_gap_us > gap_threshold_us`——**明知有盲区但未填**（预算不足或回退被中止） |

- `gap_threshold_us` = 分析时生效的 `CV_SAMPLE_GAP_FALLBACK_US`（当前 4s）**快照**；
  存快照而非读当前常量，因为该常量可能被调整，而历史行必须能自我解释；
- `achieved_max_gap_us` = 落库样本相邻时间戳最大差；
- **为什么存实际最大间隔而不只存布尔**：布尔无法回答"差多少"，
  召回层加权与后续 UI 呈现都需要程度信息；且该值 O(1) 可算（样本已按时间排序）。

**既有行的回填**：迁移 v23 将存量行默认置 `full`。**该默认值是准确的**——
存量行全部产生于"无条件回退"的旧行为：凡 `max_gap > 4s` 者必已回退至 ≤4s，
故所有存量行都满足 `achieved ≤ threshold`。回填需在迁移测试中断言这一点。

### 2.6 召回层消费

`_cv_scenes` 排序键对 `density_status = 'sparse'` 的分析**降权**（不排除）。
理由：sparse 信号仍有价值（切点、人脸仍有效），只是运动能量粒度粗——
与既有"误检代价是排序偏移而非丢段"的裁决（`AI_2_CV_SIGNALS_PLANNING_GATE` §4）一致。
**具体权重以测试钉死，不做运行时可调。**

## 3. 验收（LiuKeAi）

### 3.1 单测（Core）

1. 预算公式：正常 / 触下限 / 触上限 三档；
2. 估算模型：已知分辨率×帧率×编码 → 预期投影值；未知编码走保守分支；
3. 准入判断：投影超预算 → 不回退；未超 → 回退；
4. `analyze_video` 中途取消：置位后子进程被终止、抛 `JOB_CANCELLED`、无孤儿进程；
5. 中止语义区分：作业取消 vs 回退中止 两条路径互不误判；
6. 迁移 v23 逐版本测试；`density_status` CHECK 约束；
7. 召回降权：sparse 与 full 的排序差异可断言。

### 3.2 集成（真实素材）

1. **4K60 长 GOP**（`test-assets/generated/4k60/hevc-gop5s-60s.mp4`）：
   **墙钟 ≤ 预算**（实测基线 40.5s → 目标 ≤10s）；`density_status = 'sparse'`；
   样本数回落为 I 帧数（12）而非加密后的 60。
2. **1080p 长 GOP**（lichun，真实素材）：**仍走回退**、`density_status = 'full'`、
   样本数 167 不回归。
3. **4K60 常态 GOP 1s**（`gop1s-60s.mp4`）：不回退、`full`、墙钟 ≤ 预算（基线 5.4s）。
4. **回归**：`STATUS.md` §4 的 **P1/P2 必须保持绿**——本单正改动它们守护的代码路径。

### 3.3 性能

| 项 | 目标 |
|---|---|
| 4K60 长 GOP HEVC 完整作业 | **≤ 预算**（基线 40.5 s/分 → 目标 ≤10 s/分） |
| 1080p50 常态（dance） | 不回归（基线 4.7–5.4 s/分） |
| 1080p 长 GOP（lichun） | 不回归（基线 3.6–3.7 s/分） |

证据按仓库惯例入 `evidence/`。

### 3.4 契约与隐私

- `PROTOCOL_VERSION` **不动**；新字段为**增量可选**，旧客户端不读不受影响；
- **零 egress 增量**——预算、估算、中止全部本地；
- 迁移 v23 附逐版本测试。

## 4. 风险

| 风险 | 对策 |
|---|---|
| 估算模型高估 → 误伤本可承受的素材 | 误差方向安全（偏省时）；deadline 兜底；模型随实测校准并记录 |
| `analyze_video` 中途取消引入孤儿进程 | 单测显式断言无孤儿（3.1.4）；kill + wait 成对 |
| 把用户取消误判为回退中止 → 错误产出 sparse 结果 | 判定顺序显式化（§2.4）+ 专项用例（3.1.5） |
| 预算上限 300s 被超长素材耗尽 `light` 令牌 | 上限即为此设；且 `cv_analysis` 优先级 3 低于 waveform（2），不饿死用户可见任务 |
| sparse 降权使无语音素材召回质量下降 | 只降权不排除；权重以测试钉死；后续用评测集（W0.4）验证 |
| 本单改动 P1/P2 守护的路径导致回归 | P1/P2 为强制回归项（3.2.4），红即停 |

## 5. 开放问题（实施前裁决，ZhangSan）

1. **`algorithm_version` 是否递增？**
   本单不改变信号**计算**（`frame_signals` 不变），但改变**采样决策**；
   且 §2.3 的 deadline 兜底使同一素材在**不同性能的机器上**可能得到不同密度
   （快机回退完成、慢机中止）。
   **倾向：不递增。** 理由：①信号计算未变，递增会触发全量重分析而无信号收益；
   ②"同一 `algorithm_version` 意味着可比密度"这一隐含依赖，**已由 `density_status`
   显式承担**——这正是该字段存在的意义；③存量行回填 `full` 是准确的（§2.5）。
   **但需确认**：召回层不得再假设"同版本 = 同密度"，须实际消费 `density_status`。
   **若不递增，则本单必须包含 §1.1 第 5 项（召回层消费）才算完整**——否则依赖被破坏而无替代。
2. **`analyze_video` 的 `progress` 参数如何处理？**（§0.4 发现 2）
   三选一：(a) 本单顺带实现细粒度进度；(b) 显式删除该参数（承认它从未生效）；
   (c) 登记为独立小单、本单不动。**倾向前两者之一**——留一个永不生效的参数是陷阱。
3. **取消检查的粒度**（每 N 帧 vs 每 X ms）——实施时按实测开销定值。
4. **`density_status` 是否需要第三个值**（如 `partial`，表示回退被中止但部分生效）？
   倾向**不需要**——回退中止即丢弃全部回退结果，不存在部分生效状态。
