# ADR-0005：CV 采样密度策略——预算约束下的密度旋钮

- 状态：已批准
- 日期：2026-09-24
- 记录人：LiuWei（架构师），基于 4K60 性能标定与帧间依赖实测
- 决策人：用户（产品负责人）于 2026-09-24 批准，采纳"三杠杆并用 + 分三阶段"建议
- 关联：`CV_SKIP_FRAME_PLANNING_GATE_2026-09-20`（本 ADR 修订其 §1.2/§4 的"阈值可配"要求）、
  ADR-0004 D6（采样密度与长 GOP 空洞）、`AI_2_SKIP_FRAME_IMPLEMENTATION_2026-09-24.md` §4.2、
  `docs/STATUS.md` §4 承诺 P7
- 实施：ZhangSan（Core）；验收：LiuKeAi

## 背景

**触发事件**：2026-09-24 完成 4K60 档性能标定（此前从未测量）。用合成素材
（H.264 / HEVC × GOP 1s / 5s，60s，码率对齐真实量级 48–51 Mbps）实测：

| 素材 | 回退 | 有效 s/分 | 门（≤10） |
|---|---|---|---|
| 4K60 H.264 GOP 1s | 否 | 1.6 | ✅ |
| 4K60 HEVC GOP 1s | 否 | 2.8 | ✅ |
| 4K60 H.264 GOP 5s | **是** | 15.4 | ❌ |
| 4K60 HEVC GOP 5s | **是** | **38.3** | ❌ |

**根因**：`CV_SAMPLE_GAP_FALLBACK_US`（4s）是常量，而回退（全量解码）的成本随
分辨率 × 编码放大——1080p H.264 全量 1.1 s/分 → 4K60 HEVC 37.3 s/分，**34 倍**。
这正面印证了规划门 §1.2/§4 那条从未落实的"阈值**可配**"要求。

**关键实测（推翻初版方案）**：长 GOP 内 seek 取帧的成本与 GOP 内偏移成正比——
HEVC 4K60 / GOP 5s 下，seek 到 GOP 内 2.5s 处取 1 帧 **1.92s**，0.5s 处 **0.61s**。
因帧间依赖，取 GOP 中间帧必须从该 GOP 的 I 帧解码过来，**seek 跳不过这份工作**。

**因此采样间隔 T 与 GOP 长度 G 只有两种情形**：

- **T ≥ G**：只取 I 帧即够 → 便宜（4K60 实测 1.6 / 2.8 s/分）
- **T < G**：必须从 I 帧往后解 → 成本逼近甚至超过顺序全解（13.9 / **37.3** s/分）

**没有"又密又便宜"的选项**——这是帧间编码的物理约束，不是实现问题。

## 决策

### D1 · 采样密度：把 fast/full 二值选择改为**预算约束下的连续密度**

**内容**：`run_analysis_job` 不再做"快路径 → 检测空洞 → 要么全量回退要么不补"的二值判断。
改为：先估算"达到目标采样密度所需墙钟"，与作业预算比较；预算不足时**退到预算允许的密度**
（可落在"仅 I 帧"与"全量解码"之间的任意中间粒度），而非二选一。

**理由**：二值选择在 1080p 上工作良好（全量便宜，回退可承受），在 4K60 上失效
（全量不可承受，二选一退化为"要么超门、要么留盲区"）。真实可用的策略空间是**连续的**。

**后果**：
- 需要**解码成本模型**（分辨率 × 帧率 × 编码 → 每秒源素材的解码耗时）。该模型同时是 D2 的前置。
- 规划门 §1.2/§4 的"阈值可配"要求由本决策**取代并升级**——不再是调一个阈值常量，
  而是选择密度。
- `algorithm_version` 需再次递增（采样策略语义变化）。

### D2 · 诚实降级：密度低于目标时必须如实标记

**内容**：分析记录**实际达成的采样密度**；低于目标时标记 `sparse`，并在召回层与 UI 中如实呈现。

**理由**：D1 允许在预算不足时降低密度。若不加标记，用户与召回层会把"稀疏采样"当作
"完整信号"使用——这正是当前 `sparse` 语义缺失的缺口。**宁可承认信号弱，不可静默降级。**

**后果**：`cv_analyses` 需要记录目标密度与实际密度（迁移）；召回层排序需消费该标记；
UI 需呈现。**这是本 ADR 中唯一触及契约与存储的部分。**

### D3 · 硬件解码：作为机会性增益，不作为唯一解

**内容**：探测到可用的硬件解码器（QSV / NVENC / AMF / CUDA）时启用，抬高同一预算下
可买到的密度上限；不可用时回退软件解码。

**理由**：D3 与 D1 是**相乘**关系——它让同样的解码工作更快，从而在同一预算内买到更高密度。
但依赖用户 GPU，不能作为唯一答案（否则无 GPU 用户永远拿不到高密度）。
**本机实测 QSV 可用（Intel Iris Xe），因此该增益在目标环境可兑现。**

**后果**：需要解码器探测与能力登记；不得改变"无 GPU 时功能仍完整可用"的既有保证。

### D4 · **否决**：定点补洞（targeted gap-fill）

**内容**：明确否决"回退时 seek 到空洞附近只解几秒"的方案。

**理由**：实测证明它**比全量解码更慢**。60s / GOP 5s 素材做 1s 采样需 60 个采样点，
GOP 内偏移 0/1/2/3/4s 循环、平均偏移 2s → 平均每点解 ~1.5s → 合计 **~90s**；
而顺序全量解码只需 **37.3s**。逐点 seek 是重复劳动，顺序全解是共享劳动。

**记录否决的原因**：该方案在直觉上极具吸引力（"只解需要的部分"），
**初版方案文档正是据此把它推荐为"真正的修复"**。不留下否决依据，后来者会重新提出。

### D5 · 分三阶段实施

| 阶段 | 内容 | 依赖 | 性质 |
|---|---|---|---|
| **1** | 解码成本模型 + D2 诚实降级 | 无 | 诚实性修复，工作量小。**让 4K60 长 GOP 不再静默超门** |
| **2** | D1 密度旋钮（取代二值选择） | 阶段 1 的成本模型 | 真修复 |
| **3** | D3 硬件解码 | 阶段 1/2 | 机会性增益 |

**前置约束**：阶段 2 触碰 `run_analysis_job`。**在该代码被改动前，必须先补
`STATUS.md` §4 的 P1/P2**（sha256 对拍锁、长 GOP 回退触发测试）——否则等于在
无护栏的路径上叠加改动（该判断与总纲 §6 W1.2 的约束一致）。

> **前置已满足（2026-09-24）**：P1/P2 已作为集成测试落地并核销
> （`test_cv_signals_real.py`：`test_short_gop_fast_and_full_paths_are_byte_identical`
> 含反向对照、`test_long_gop_triggers_full_decode_fallback` 三段断言）。
> **阶段 2 可以开工。**

## 影响

- **性能门**：4K60 常态（GOP ≤ 2s）已达标并保持；长 GOP 由阶段 1 转为"如实标记"，
  由阶段 2 转为"预算内尽可能密"。
- **存储/契约**：D2 需迁移（记录目标与实际密度）与召回层/UI 消费。**PROTOCOL_VERSION 不动**。
- **隐私**：全部决策**零 egress 增量**——成本模型、密度选择、硬件探测均在本地。
- **既有承诺**：本 ADR **取代**规划门 §1.2/§4 的"GAP_THRESHOLD 可配"表述（升级为密度选择）；
  `STATUS.md` §4 的 P7 由"待裁决"转为"已裁决"，P1/P2 由"可选补测"升级为**阶段 2 的前置**。

## 否决方案

- **定点补洞**：见 D4——实测更慢。
- **维持 fast/full 二值 + 只调阈值**：否决——阈值是单点，无法表达"预算内尽可能密"；
  且 4K60 上无论阈值取何值，T < G 时都只能二选一。
- **放弃长 GOP 素材的密度**：否决——等于对一类真实素材静默降低信号质量，违反 D2 精神。
- **只做硬件解码**：否决——依赖 GPU，无 GPU 用户得不到改善。
- **对 4K60 素材统一降级为"仅 I 帧"**：否决——常态（GOP ≤ 2s）下 I 帧密度已足够且达标，
  统一降级是无谓损失。
- **引入第三方节拍/解码优化库解决**：否决——问题在采样策略与成本模型，不在库。
