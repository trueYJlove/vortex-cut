# 浅色主题系统性治理：语义令牌层 + 两道机器守卫（2026-11-11）

对应实现登记：`docs/STATUS.md` §4 **P224**。

**来源**：用户先给 3 张浅色截图指出具体缺陷，修完后仍反馈
「项目列表浅色模式下还是不正常，你不是说有很多硬编码吗？是不是应该用规范的方式
彻底解决这个问题？」——即**要求根治，不接受逐点修补**。

本文记录三件事：为什么要从头做、令牌层怎么建的、以及**过程中我搞坏的两件事**
（都是真实回归，都靠工具查出来，不是自查发现的）。

## 1. 为什么逐点修补不可能收敛（先量化，再动手）

改前对 `styles.css` 做规则级扫描（`.tmp` 里的解析脚本，跳过注释、跳过
`html[data-theme="light"]` 覆盖规则、跳过 `var(--x, fallback)` 的兜底值）：

| 指标 | 改前 |
|---|---|
| 规则总数 | **2116** |
| 规则内颜色字面量声明次数 | **587** |
| 受影响规则数 | **418**（占 19.8%） |
| 唯一色值 | **248** |

关键不是数量，是**分布**——这是判断"能不能靠逐点修补收敛"的依据：

| 出现最多的 N 个色值 | 覆盖声明数 |
|---|---|
| 10 | **26.4%** |
| 30 | **44.3%** |
| 50 | **55.7%** |
| 100 | **74.1%** |

**前 30 个色值只覆盖 44%，剩下 156 个唯一色值摊在余下 56% 里，长尾极重。**
这意味着逐点修补的完成度会随轮次线性爬升而非收敛，用户会在新位置不断遇到同类问题
——事实上这就是"项目列表还是不正常"的成因：上一轮我把下拉框里看得见的两处修了，
同一面板内还有 `切换项目`（对比度 **1.18**）和 `项目管理`（**2.26**）两处没看见。

**所以本轮换做法：不修颜色，改颜色的产生方式。**

## 2. 令牌层：243 个语义令牌，深色值精确等于被替换的字面量

在样式表末尾「令牌终值」标记**之前**插入成对的两块：

```
:root {                      /* 深色 */
  --ink-1: #e8edf0;
  --surface-1: #0e1318;
  ...
}
html[data-theme="light"] {   /* 浅色 */
  --ink-1: #1a1a1f;
  --surface-1: #ffffff;
  ...
}
```

**家庭**：`--ink-*`（文字 98）、`--surface-*`（底 76）、`--rgba-*`（半透明 194）、
`--line-*`（边框 44）、`--brand-*`（18）、`--warn-*`（14）、`--ok-*`（8）、
`--danger-*`（8）、`--info-*`（2）、`--fixed-*`（6，主题无关的黑/白/阴影环）。

**核心设计：深色逐像素不变。** 每个令牌的深色值都**精确拷贝**它替换掉的那个字面量。
近似色（`#e8edf0` / `#e9eef0` / `#edf1ef`）**各自独立成令牌、不合并**，
所以深色是纯改名、零像素变化——代价是令牌名带后缀（`--ink-1-b`、`--ink-1-c`…）。

替换是**脚本化逐行**做的（`.tmp/rebuild3.mjs`）：跳过任何以 `--` 开头的定义行，
其余 587 处声明全部换成 `var(--token)`。

**结果**：规则外颜色字面量 **587 → 0**。

## 3. 两道机器守卫（`apps/desktop/tests/theme-token-coverage.test.ts`）

没有守卫，令牌层会在下一次改动里退化回字面量。四条断言：

1. **样式表能被解析出 >1500 条规则** —— 防止解析器本身失效导致后面几条恒真。
2. **普通规则不得出现颜色字面量** —— 除令牌块与 `[data-theme="light"]` 覆盖规则外，
   任何 `#hex` / `rgb()` / `hsl()` 都失败。`var(--x, #fallback)` 的兜底值豁免。
   *这条测试第一次跑就抓到了我漏掉的东西：我只统计了十六进制，它发现 `rgba()`
   同样是硬编码，一次性多出 177 处。*
3. **令牌层不得重定义别处已有的令牌名** —— 见 §4.1，这是本轮最重要的守卫。
4. **深色与浅色令牌一一配对** —— 243 对，缺一即红。

## 4. 过程中我搞坏的两件事（都记下来，因为都是自查发现不了的）

### 4.1 令牌重名抢走了画布的取色（真实回归，深色受影响）

令牌层给 `#3c4a56` 起名 `--tl-tick-major`。但这个名字**早就存在**：

```
styles.css:3708  :root { --tl-tick-major: #8a95a5; }        ← 时间线画布的主刻度色
TimelineCanvas.tsx:463  cssColor("--tl-tick-major", ...)     ← 画布这么读它
```

我的令牌块位置更靠后，**后定义获胜**，于是深色时间线主刻度从 `#8a95a5` 变成
`#3c4a56`（暗了 1.5 倍）。

**为什么测试和 CSS 检查都发现不了**：没有任何规则引用错——是"名字被抢了"。
画布取色走 `getComputedStyle`，静态检查里完全隐形。**是逐像素 diff 发现的：
深色截图有 119 个像素不一致，全部落在标尺主刻度那一列（x = 390/540/690/…/1290，
正好是主刻度间隔）。**

修法：改为 `--tl-tick-rule-major`；同时给那条**从未被引用**的
`.timeline-tick.major` 规则（TSX 里搜不到任何使用处）也指向新名字，避免留一个死令牌。

**守卫第 3 条就是为它写的**：找出"整块只由 `--x: value` 构成"且声明数最多的
`:root` / `html[data-theme="light"]`，层内任何名字若在层外另有定义即失败。

> **这条守卫第一版是错的，必须记下来**：我用"同名恰好出现两次"来识别令牌层。
> 而真正的重名让 `--tl-tick-major` 出现 4 次，于是它被判为"层外"，
> 240 个令牌一起漏出识别集，**守卫恒真——注入变异体照样全绿**。
> 改成结构性识别（整块纯声明 + 声明数最多）后，再投变异体才正确变红。

### 4.2 批量替换把令牌定义自己替换掉了

第一版替换没有跳过 `--` 开头的行，于是刚写进去的
`--fixed-white: #ffffff;` 被改写为 `--fixed-white: var(--fixed-white);`（231 处），
全部解析为空 → 面板透明。

同类第二处：插入令牌块时 CSS 括号失配（一度 340 处不平衡），手补越补越乱。
**最后放弃手补，回到 `.tmp/styles-backup.css` 用一次性生成脚本重做**，才收敛。
这个教训写进脚本注释：**结构性问题不要手工修补，用一次性生成覆盖。**

## 6. 本轮唯一一处"改颜色本身"的地方

`--ink-4-b`（最低一档辅助文字，用于 `footer` 的「后台空闲」）在浅色下是
`#9a9aa2`，落在 `rgb(236,236,237)` 页脚上对比度 **2.37**。

这个令牌**不是**改名能解决的——它在深色下是 `#556067`（对比度 2.85），

**只改了浅色侧的值**（`:root` 那份不动），所以深色零影响。

页脚其余文字实测：`已保存` / `Core 已连接` / 版本号 = 2.90，
`多平台导出`…`设置` = 5.78。2.8–2.9 是这类次要状态文字的合理档位。

### 7.1 关于并行跑全量的偶发红（如实记录）

首次并行跑全量时 6 个文件红、第二次 5 个红、且**红的文件不同**，每个文件单跑全绿。

- `preview-audio-cache.test.ts:57` —— `await sleep(80)` 后断言

放宽超时救不了**。本轮用 `--no-file-parallelism` 串行跑作为验收口径，
**不把"串行跑绿"当作"没有偶发问题"**——这笔账登记进 STATUS。

## 8. 追加（2026-11-15）：深色下项目下拉没有 hover

**用户反馈**：「项目下拉列表鼠标上下滑动时，有一个 hover 效果，浅色模式下正常，
深色模式下看不到」。

**实测根因**（不是"颜色太淡"，是**同一个值**）：

```
.project-switcher-dropdown > button:hover { background: var(--ws-raise); }   /* 777 */
.editor-shell .project-switcher-dropdown  { background: var(--ws-raise); }   /* 5191 */
```

悬停色与下拉面板自身底色**是同一个令牌**。深色下两者都解析成 `rgb(32,32,36)`，
对比度 **1.00**——hover 确实发生了，只是画在同一颜色上。

**浅色下"正常"是巧合，不是设计**：

| 主题 | 面板底 | 悬停底 | 悬停是否可见 |
|---|---|---|---|
| 深色 | `#202024` | `#202024` | ❌ 对比 1.00 |
| 浅色 | `#ffffff` | `#e8e8ea` | ✅ 对比 1.22 |

浅色那 1.22 来自 `[data-theme="light"] button:hover:not(:disabled)`
（`:15`）这条**全局通用规则**抢先覆盖 —— 它比 `.project-switcher-dropdown > button:hover`
特异性更高。也就是说浅色靠的是另一条规则的副作用，规则本身在两种主题下都是错的。

**修法**：新增 `--ws-hover` 令牌，与 `--ws-raise`（面板底）分开：

```
深色  --ws-hover:#2f2f35   （对面板 #202024 对比 1.22）
浅色  --ws-hover:#e8e8ea   （对面板 #ffffff 对比 1.22）
```

两档**对比度取同一个值 1.22**，是照浅色既有观感（`#e8e8ea`）标定的，
深色不再"更淡或更重"。浅色侧取值与原观感完全相同，**视觉零变化**。

### 8.1 同源缺陷一：选中项悬停后"看起来没选中"

`.active` 的强调底会被 `[data-theme="light"] button:hover`（特异性 0,3,1）
盖掉 `.active`（0,2,1），实测选中行悬停后从 `rgba(15,158,134,.12)` 变灰底。
加 `.project-switcher-dropdown > button.active:hover` 显式锁回强调底。

### 8.2 同源缺陷二：素材库选中页签悬停后掉色

`.editor-shell .library-toolbar button:hover` 把 `background` 设成
`var(--ws-raise)`，冲掉了 `:first-child` 的强调底。实测：
深色 `rgba(53,214,174,.12) → rgb(32,32,36)`、浅色 `rgba(15,158,134,.12) → rgb(255,255,255)`。
补 `:first-child:hover`（特异性 0,5,1）锁回。

### 8.3 新增第三道守卫

`theme-token-coverage.test.ts` 增加一条：**悬停底色不得与它所在容器的底色同色**。
对每条含 `:hover` 的规则推出其容器选择器，若容器背景用了同一个令牌即失败。

**这条守卫写错过两次，都是"恒真"型错误，记下来**：

1. 拿 `:hover` 去匹配 `rule.body` —— 选择器不在 body 里，结果恒空；
2. 改用"选择器含 panel/dropdown 字样"当容器判据 —— 把
   `.pp-panel .pp-sub.pp-active` 这类**选中态底色**误判成面板底色，
   `--ctl-bg-hover` 全表命中，满地假红。

最终改为**从 hover 选择器自身推导容器**（去掉 `:hover` 及其后、取 `>` 左侧或
最后一段之前），只精确比对那一个容器。变异验证：把 hover 改回 `--ws-raise` →
**红**且只报 L777 这一条；恢复 → 绿。
