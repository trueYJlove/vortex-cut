## 1. 背景与问题

B13-R 判别:F02(900s@640×360@30,27000 帧)Tab WS 16.6GiB 平台为
**Chromium 层有界池高水位**(unique 帧数饱和,~600KB/帧,应用层无泄漏)。
应用侧无可修对象后,唯一可行动的结构性方向 = **降低解码输入分辨率**
(B11 代理,帧字节随像素数缩小,池结构不变、总量降档)。

本备忘录回答:代理降档对 F02 类"长素材"是否真实有效、若有效如何接线。

## 2. D1 spike 设计(工具已入库,待实测)

**方案**:夹具级替换——`F02P` 场景 = 与 F02 完全相同的装配(900 段/900
字幕),仅媒体换为 320×180/900s 源(帧字节 4× 减小)。不动
source-resolver 默认策略,不触发代理作业;测的是同一问题(解码驻留随
帧字节的缩放),侵入最小。

**判定双轨(重要——现行预测器缺分辨率项)**:

| 模型 | 预测值 | 说明 |
|---|---:|---|
| 解析缩放律(本 spike 主判定) | **≈4.4GiB**(0.4GiB base + 27000×600KB×(320×180)/(640×360) = 0.4+3.96) | B13-R"帧字节 4× 减小"假设的直接推论;允差 ±25% → 3.3–5.5GiB |
| 现行 `predictResidencyBytes` 实现值 | 16.35GiB | **实现无 w×h 缩放项**(600KB/帧常数,w/h 仅用于 ≥4× 封顶分支)——已知模型缺口,spike 结果决定是否补项 |

**判定**:
- 实测平台落入 3.3–5.5GiB → 缩放律成立,现行预测器补 w×h 项后可作
  D2 触发线;
- 实测平台 ≈16GiB → 池高水位不随帧字节缩放(按 unique 帧数),**代理
  降档对 F02 无效**——如实登记,B11-D 关闭,方向仅剩 Chromium 上游/
  接受现状;
- 介于两者 → 按实测标定,登记曲线。

**运行**(实际机器时 58.2min——off/on 双通道共 11 次启动,原估 35min
只计了 5 个播放窗,低估一半,登记修正):

```text
python tools/performance/make_fixtures.py --output <空目录> --scenarios F02P --allow-large
AIVS_PERF_RUN=1 AIVS_PERF_SCENARIOS=F02P AIVS_PERF_FIXTURES=<目录> \
  AIVS_PERF_RESULT=<输出目录> npx playwright test apps/desktop/e2e/performance-editor.spec.ts --grep F02P
```

（直连 playwright 时 spec 读取 `AIVS_PERF_RESULT/run-config.json` 的
`code_fingerprint`——runner 的 KNOWN_SCENES 不含 F02P,须按 runner 同款
算法预置该文件;本轮实测即此路径。）

### 2.1 D1 实测结果(2026-09-12,同机插电,v1 构建指纹 42585dad8c9d)

| 指标 | F02P(320×180) | F02(640×360,同日 v1 轮) | 差 |
|---|---:|---:|---:|
| Tab WS 平台(5 轮中位) | **16,649MB**(极差 28MB) | 16,707MB | **-0.35%** |
| 解码量/300s | 7,938(26.5/s,全速) | ~7,860(26.2/s) | 同型 |
| ready 中位 | 5,507ms | 5,771ms | 同型 |

夹具防御性核验:ffprobe 确认 F02P.mp4 = 320×180/900s/30fps h264
(F02 = 640×360,同配方),测量有效性无虞。

**判定(命中双轨第 2 分支):实测平台 ≈16.6GiB,与 640×360 基线统计
同值(-0.35% 在轮内噪声内)——解析缩放律(≈4.4GiB)证伪,代理降档
(降低解码输入分辨率)对 F02 类"长素材"的解码驻留平台无效。**

归因细化:每 unique 帧驻留成本 16.65GB/27000 ≈ 631KB/帧(320×180)
≈ 630KB/帧(640×360)——**该成本与源分辨率无关**,不是解码帧字节
(后者 4× 缩小却无效应),是 Chromium 侧按帧计的固定成本。B13-R 的
"~600KB/帧"锚定据此修正定性:常数项有效,**现行
`predictResidencyBytes`(无 w×h 项)不需要补分辨率项**——其对两个
实测点的偏差为 -2.1%(640×360)/ -1.9%(320×180),预测力反而优于
缩放律。B11-D 方向如实关闭;F02 类内存残余路线仅剩 Chromium 上游
行为变更或接受现状(平台有界、2400s 无晚发增长,见 B13-R)。

## 3. D2 三问(待 LiuWei 裁决;D1 实测后各问已可给推荐结论)

### 问 1:auto 模式接入驻留预测的降档触发线?

- D1 结论后**推荐:不实施降档触发线**。"超预算时请求代理"的语义失去
  依据——代理降档不降低驻留平台(D1),触发线无处兑现。
- 驻留预测(`predictResidencyBytes`,常数模型)仍可继续用于**导入/装配
  评估一次的会话预警**(B13-R R3 已落地的驻留平台预测护栏)——预警"高
  驻留"仍然真实(16.6GB 平台可预警),只是缓解手段不再是代理降档。
- 备选(原提案)已按上述证据修正;若产品仍想要"预览质量:原片/代理"
  手动选择,属独立的功能诉求(画质/带宽动机),不属本决策轮范围。

### 问 2:是否增设低于源短边的档位?

- **推荐:不增设。**F02 类小源长素材的代理档(preview-270/180)即便做
  出来也不改变驻留平台(D1)——本问存在的前提("降档省内存")被证伪。
- F04(4K)用 preview-540 得 4× 的既有结论不受影响(大分辨率长源的
  收益场景此前就存在,与 D1 的 F02 类"小源"结论正交;如需重测可另立,
  D1 结果提示其收益同样存疑——**待 4K 源同型 spike 才能下结论,本轮不
  预设**)。

### 问 3:代理质量降级的 UX 登记

- **推荐:随方向关闭,无新增 UX。**无降档触发线、无新档位,代理降级
  仅存在于既有 preview-540/720/1080 对大源生效的场景,沿用 B11 既有
  口径("质量变化记录为代理降级,不混同原片基准")即可,无新增决策。
