# P203 复测：10-bit HLG HEVC 点「播放」后是否仍挂死（2026-11-05）

> 状态源引用 `docs/STATUS.md` §4 **P203**。本文只记录本轮实测事实与证据等级。
> 前置诊断：`evidence/2026-11-01-iphone-hevc-blockers/P203_DIAGNOSIS.md`、`P203_ENVIRONMENT.md`。
> 本任务为**测量**，产品代码零改动（见 §7）。

## 0. 结论

**判定：C — 不再挂死，但没走代理。**

- **【观测】10-bit HLG HEVC（`raw-remux.mp4`）点「播放」后，渲染进程主线程全程存活**：
  点击后 18 秒内 `document.title` 心跳镜像从 32 单调涨到 217，`webContents.isCrashed()` 恒 false。
  P203 描述的「主线程 100% 堵死、界面无响应」**在本 HEAD 上未复现**。
- **【观测】** 播的是 **FFmpeg 软解后端**（`decode_backend="ffmpeg"`、`decode_hardware=""`），不是 WebCodecs。
  【观测】WebCodecs 分支仍然产出坏帧（`output_enter {"pts":0,"fmt":null}` → `bad_frame_format`）。
  【推断】堵死不再发生，是因为该错误码已进降级正则、由 FFmpeg 后端接住（机制见 §3）。
- **【观测】代理未生效**：点播放前后 `getPreviewSource` 均为 `status=ready, mode=original`；
  代理作业 `6f1bb1a8…` 在点播放 20 秒后仍 `status=running, progress=0.137, stage=proxy:libopenh264:fallback`。
  **即：本轮没有一帧是代理解出来的。**

C 的具体路径与后端见 §3。

## 1. 必须先说的测量方法问题（本轮最重要的发现之一）

**原探针的「主线程堵死」判据是恒真的，从未真正测过。**

原版本 `diag-p203-hang.electron.spec.ts:79-82`：

```ts
const st = await Promise.race([
  page.evaluate(() => {...}),
  Promise.resolve("EVAL_BLOCKED"),   // ← 已 resolve 的 promise
]);
```

`Promise.resolve()` 是**已完成**的 promise，在微任务序中**永远先于** `page.evaluate`
（后者至少要走一次 CDP 往返）胜出。**因此原探针无条件打印 `EVAL_BLOCKED`，
与主线程是否真的堵死无关。**

**【观测】** 本轮 **Run 2**（8-bit 对照，历史认定「不挂死」的素材，已换成真定时器判据）
在 +6s 后仍连续打印 `EVAL_BLOCKED`，**而同轮 title 心跳全程 10Hz 满速、`crashed=false`**
——**对照素材既"报堵死"又"明显活着"**，直接反证「EVAL_BLOCKED ⇒ 主线程堵死」这个等式不成立。

>原判据恒真这一点是**读码得出**【观测（源码）】，未用原版跑一轮去实证：
>本轮四次运行全部使用**修正后**的判据（Run 1 起即已含真定时器 `AIVS_PROBE_EVAL_CAP_MS`）。
>故「原版恒真」与「修正后仍超时但主线程活着」是**两条独立证据**，都指向同一结论：
>EVAL_BLOCKED 不能作为堵死判据。

**修法**：改为真定时器竞速（`AIVS_PROBE_EVAL_CAP_MS`，默认 2000ms），
并加一条**不依赖渲染进程配合**的独立通道：

- 渲染进程主线程每 100ms 写 `document.title = "hb:<心跳>|cf:<合成帧>|df:<丢帧>|be:<后端>|hm:<hdr>"`。
- title 由**浏览器进程**缓存并经 IPC 推送，主进程 `BrowserWindow.getTitle()` 读取
  **不需要渲染进程响应** ⇒ 主线程真堵死时 title 冻结，主线程活着时 title 持续推进。
- 这条通道能把「应用真挂死」与「CDP evaluate 通道被饿死」分开——Run 2 正是靠它定案的。

>[推断] Run 2 中 `page.evaluate` 在 +6s 后连续超时、而 title 心跳全程 10Hz 满速、
>`crashed=false`，说明**超时发生在 CDP 通道而不在渲染主线程**。该现象与 P203 无关
>（8-bit 对照同样出现），且**不影响本轮判定**——判定用的是 title 心跳与 metrics 读数，
>二者都成功采到。

## 2. 四项必需测量

### (1) 代理作业是否被创建、是否 succeeded

| 时点 | job_id | status | stage | progress |
|---|---|---|---|---|
| 导入后 | `6f1bb1a809904a9fbaf20390659b9942` | running | running | 0 |
| 点播放前 | 同一作业 | running | running | 0 |
| 点播放后 +20s | 同一作业 | **running（未终态）** | `proxy:libopenh264:fallback` | **0.137** |

**【观测】作业被创建并确实在跑，但 20 秒内没有 succeeded，也未 failed。**
「导入即转」路径（`App.tsx:1707`）**是无条件触发**的，所以 10-bit 素材必然会登记代理作业
——这一点与「`over_budget` 攒不出 30 个样本」的怀疑**无关**：挂死类缺陷不会拦住导入路径的登记。

>[推断] 未完成的原因是耗时而非失败：素材 146.96s / 3526 帧 / 3840×2160，
>实测本机 ffmpeg 把 5 秒 4K 10-bit 转成 1080p 代理需 **2856ms** ⇒ 整段外推约 **84 秒**，
>而本轮采样窗仅到导入后约 20 秒。`stage` 里的 `:fallback` 表示硬编不可用、
>已回退到软件 `libopenh264`，这也与耗时一致。

### (2) sourceResolver 最终解析到 proxy 还是 original

**【观测】** 三次采样（导入后 / 点播放前 / 点播放后）`getPreviewSource(mode="auto")` 均为：

```json
{ "status": "ready", "mode": "original", "job_id": null,
  "profile_id": "preview-720-v1",
  "coded_width": 3840, "coded_height": 2160, "rotation": 270 }
```

**⇒ 解析到 original（原片），不是 proxy。**
`source-resolver.ts:42` 只在 `status==="ready" && mode==="proxy"` 时用代理票；
本素材 `mode` 恒为 `original` ⇒ 走原片票。
注意 `coded_width/height = 3840×2160`、`rotation=270` 也是原片几何（代理应是烘焙旋转后的
竖版小尺寸），**双向印证未走代理**。

### (3) 点「播放」后主线程是否还能响应

**【观测】能响应，全程未堵死。**

- `document.title` 心跳镜像：点击前 `hb:32` → +19.7s `hb:217`。19.7 秒涨 185 拍，
  约 **9.4 拍/秒**（设计值 100ms/拍 = 10/秒）⇒ **主线程没有停顿**。
- `BrowserWindow.webContents.isCrashed()`：12 次采样**全部 false**；`isDestroyed()` 全部 false。
- `page.evaluate` 从 +1.5s 到 +18s **12 次全部成功返回**（耗时 9–1086ms），
  **无一次 EVAL_BLOCKED**。对比 Run 2（8-bit 对照）反而出现 EVAL_BLOCKED，
  说明 10-bit 这一轮的主线程响应性比对照组读数还好——再次印证 EVAL_BLOCKED 不是挂死信号。

### (4) 能播 ⇒ `__aivsPreviewMetrics` 的 decode 口径

**【观测】** 最终快照（`+19.7s`）：

```json
{ "decode_backend": "ffmpeg", "decode_hardware": "",
  "decode_ms_p50": 14.5, "decode_ms_p95": 42.9,
  "dropped_frames": 0, "composed_frames": 27,
  "last_error": null,
  "hdr_media": true, "hdr_decodable": false,
  "task_ms_p50": 0.1, "task_ms_p95": 0.2,
  "chain": { "I0": { "fed": 30, "inFlight": [28,29,30],
                     "ring": [24,25,26,27,20,21,22,23], "shadow": -1, "last_decode": null } } }
```

- `decode_backend = "ffmpeg"` ⇒ **实际走 FFmpeg 软解**，不走 WebCodecs 硬解。
- `last_error = null` ⇒ 无残留错误。
- `hdr_media = true` / `hdr_decodable = false` ⇒ HDR 提示通道按预期工作（P203 的「检测+告知」仍有效）。
- **`composed_frames` 停在 27 不再增长，`chain.I0.inFlight=[28,29,30]`、`last_decode=null`。**

  >【观测】该停滞**不是 10-bit 特有**：Run 2 的 8-bit 对照同样从 53 帧起不再增长。
  >【观测（源码）】播放 tick 由 `requestAnimationFrame` 驱动（`preview-session.ts:2309,2311`）；
  >而本探针**从不 show/focus 窗口**（`electron.launch` 后直接取 `firstWindow()`）。
  >【推断】Chromium 对未显示/未聚焦窗口的 rAF 会节流至近乎停止 ⇒ **合成帧计数停滞是
  >无头运行方式的产物，不是产品缺陷**。故本项**不能**用来断言「画面播不动」。
  >**P203_ENVIRONMENT §12.6 的「播几秒卡一下」需要可见窗口才能验证，本轮未覆盖。**

## 3. 判定字母的依据

**C = 不再挂死，但没走代理。实际路径与后端：**

- **路径**：原片（`mode=original`），3840×2160、rotation=270 的原始 10-bit HLG 流，
  经 restricted-media 原源票直接作为解码输入；**代理票从未参与**。
- **后端**：`ffmpeg`（Core IPC 软解 / `FfmpegMediaDecoder`）。
- **它为什么不再挂死**（【观测】+【推断】）：
  - 【观测】worker trace 只有 21 行，且形态与 P203 诊断完全一致：
    `output_enter {"pts":0,"fmt":null,"decoded":0}` → `bad_frame_format {"pts":0,"coded":"3840x2160","streak":1}`。
    **WebCodecs 依然产出 `format=null` 的坏帧——SPEC §10.3 的 P010/SOFTWARE 根因没有被修掉。**
  - 【观测（源码）】坏帧现在被**识别并计数**：`decode-worker.worker.ts:544` 记
    `bad_frame_format`（含 `streak`），`:557` 抛
    `DECODE_FRAME_FORMAT_NULL: 解码器产出 format=null 的帧（10-bit HEVC 硬解已知缺陷…）`。
  - 【观测（源码）】该错误码**已纳入降级正则**：`preview-session.ts:1124`
    `/timeout|watchdog|key frame is required|DECODE_FRAME_FORMAT_NULL/i`。
    （对照 P203_ENVIRONMENT §7.3：当时该正则**不含** `DECODE_FRAME_FORMAT_NULL`，降级永不触发。
    **这正是本轮与诊断当时最关键的行为差异。**）
  - 【观测（源码）】`:1151` `deterministic = /DECODE_FRAME_FORMAT_NULL/i.test(message)`
    ⇒ 坏帧按**确定性失败**处理，首次即降级，不必攒够次数。
  - 【推断】于是会话切到 FFmpeg（`decode_backend="ffmpeg"`、`decode_hardware=""`），
    堵死路径被绕开。
  - **关键结论：缺陷根因（`fmt:null` 坏帧）仍在，但"发现即降级"的闭环已接上。**
    这解释了「为什么还产坏帧却不再堵死」。

## 5. 为什么代理没在这条素材上生效

**【观测】** 代理作业已登记且在跑（§2.1），但 `mode` 始终 `original`。

**机制（读码 + 观测交叉）**：
- 生效条件唯一：`source-resolver.ts:42` 的 `status==="ready" && mode==="proxy" && cache_key`。
- `mode` 由 Core 侧 `preview_source.describe` 决定：`proxy.status==="ready"` 才回 `proxy`。
- 本轮作业**从未到 ready**（20 秒时 progress 0.137）⇒ `mode` 恒 `original`。

**⇒ 本轮无法判定「代理生效后是否仍挂死」。** 这不是「代理触发了但没生效」，
而是「代理还没转完」。要判定这一点，需要在代理 ready 之后再看 —— 见 §8 未完成项。

**关于「`over_budget` 触达不到代理」这个怀疑：本轮证据显示它对这条素材不成立，但原因不是怀疑里说的那个。**
- **【观测】** 代理作业在**导入后立即**存在（`source@import` 采样即有 `status=running` 的代理作业），
  早于任何解码发生、早于任何 `over_budget` 判定。
- 原因：`App.tsx:1707` 的 `importAsset` 对**每个视频素材无条件**调用
  `requestProxyJobRef.current(...)`；`over_budget`（`App.tsx:1097-1105`）只覆盖
  **已导入的老素材**这条补漏路径。
- **⇒ 对本任务的上传流（新项目 + 导入 + 拖上时间线），代理登记与 30 样本无关。**
  真正卡住代理的是**转码耗时**，不是触发条件。

## 6. 观察到的、不在本任务范围内的问题（只列，不修）

1. **探针原判据恒真（已在本轮修掉，但同类写法可能仍在别处）**：
   `Promise.race([realWork, Promise.resolve(FALLBACK)])` 的 FALLBACK 恒胜。
   **P203 此前所有「EVAL_BLOCKED ⇒ 堵死」的结论都建立在这个恒真判据上，建议重新评估。**
   >关于 P203_DIAGNOSIS §0「点击播放后 18 秒内 `page.evaluate` 全部 EVAL_BLOCKED」：
   >按本文 §1，该读数无法区分「真堵死」与「判据恒真」。本轮实测同素材主线程存活，
   >故对该条历史证据的效力存疑——**但这不否定 P203 本身**（§3 的 `fmt:null` 坏帧仍实测存在）。
2. **坏帧根因未修**：`fmt:null` 仍复现，靠 FFmpeg 降级规避。任何让能力表回到 webcodecs 的路径
   （新进程、降级冷却回切）都可能重新暴露堵死风险。`FFMPEG_RETRY_COOLDOWN_MS` 回切是否安全**未验证**。
3. **探针从不 show/focus 窗口 ⇒ rAF 被节流，`composed_frames` 在两轮里都停住**
   （10-bit 停在 27、8-bit 停在 53）。**这使所有基于 `composed_frames` 增长率的结论
   在本套 e2e 下都不可用**，也让 P203_ENVIRONMENT §12.6「播几秒卡一下」无法在此验证。
   建议后续探针在 `electron.launch` 后显式 `win.show()/focus()`。
4. **`page.evaluate` / CDP 通道在 8-bit 与 10-bit 播放数秒后均超时**，而主线程与 title 心跳正常。
   机制未查（疑与大量 worker console 日志、2.5MB/轮的日志回传有关：Run 1/2 各产生
   ~34k 行 trace、~2.5MB）。**任何依赖 `page.evaluate` 在播放中取样的 e2e 都可能受此影响而误判。**
5. **代理改走软件编码**：`stage=proxy:libopenh264:fallback` 表明硬编不可用已回退；
   整段 4K→1080p 代理约需 84 秒（外推）。对 146s 的 4K 素材，用户要等约 1 分半代理才可能生效。
6. **`preview_source.job_id` 恒为 null**（即使代理作业在跑）：
   `get_preview_source` 路由只在 `generate=true && mode=proxy` 时才回填 `job_id`，
   `mode=auto` 下恒 null。`source-resolver` 不依赖该字段，但它让「代理作业在不在跑」
   无法从该端点看出——本轮只能改用 `listJobs` 逐状态查询。
