## 这份证据为什么存在

用户在 2026-11-09 指出：这三个弹窗**没有单独的原型稿**，只有一份覆盖「形态」的
结构稿（`docs/design/ui-mockups/dialog-system-v2/prototype-list-family.html`），
所以没法验收我改的是否满足要求。

这份目录补的就是这个缺口：**每个弹窗一对 before/after 截图 + 一份取值对照表**。

## 怎么验收

1. 看 `*-before.png` 与 `*-after.png`：同一场景、同视口、同主题；
2. 看下方「取值对照」：每个数字都有实测出处，不是设计声明；
3. 想复核：`apps/desktop/tests/*-align.test.ts / *-table.test.ts` 把取值锁成了断言，
   改回旧值会变红（变异验证记录在各 commit message 里）。

**偏移/置信度两个数字列全部左对齐**；分隔线用 `var(--ctl-bg)`（控件填充色）当线色。

| 项 | 改前 | 改后 |

| 单元格内边距 | 4px 6px | 9px 8px |
| 数字列对齐 | 左对齐 | 偏移 / 置信度**右对齐** + tabular-nums |

**列宽实测**（改后）：机位 102 / 状态 92 / 偏移 84 / 置信度 72 / 来源 64 / 手填 176。

### 表头与数据对齐（用户二次指出后修正）

用户看图后追问：「左对齐还是右对齐还是中间对齐，需要和其他弹窗统一起来」。

实测确认问题在**状态列**：表头 `text-align: left`，而 td 内是定宽 62px 居中的徽章，
视觉上表头偏左 22px。修法是把该列的 **th 与 td 都设为 center**（只改 th 不够——
td 仍是 left，定宽徽章靠自身居中"伪装"成居中，这也是我第一版改错的地方）。

六列最终对齐方式（表头 = 数据）：

| 列 | 对齐 | 理由 |
|---|---|---|
| 机位 | left | 变长文本 |
| 状态 | **center** | 定宽徽章居中，表头须跟随 |
| 偏移 | right | 数字列，便于纵向比较 |
| 置信度 | right | 数字列 |
| 来源 | left | 短文本 |
| 手填 | left | 表单控件 |

> 与其他弹窗的一致性：keyframe / 语义检索两个弹窗**没有表头**，不存在此问题；
> 三者共用的是「状态徽章定宽 62px 居中」这条契约，本轮未破例。

## 7 · 危险语义令牌（`danger-colors-before.png` / `danger-colors-after.png`）

**这是本轮最有价值的发现，且计划外的。**

扫描 `.modal` 作用域内的硬编码时，发现「危险 / 错误」语义用了 **9 种红色**：

```
#f0a1a5  #e88b8f  #f0b9b2  #f2b8b5  #edb9bb
#d9b4b4  #f2797d  #f05a5f  #ee7377
```

改一处配色要翻九个地方，改漏也没人发现。实测还发现 `#f05a5f` 与 `#ee7377`
是**两个不同的 danger hover 值**——同一语义两处不一致。

### 走了两条路，第一条是错的

**先试 `color-mix()` 从 `--dlg-danger` 推导**，反解配比时发现：
`#f2b8b5` 需要 **132%**、`#f0b9b2` 需要 **128%**（超出 0–100%），
说明这些色与主色**不是线性混合关系，是各自挑的**。硬推导致 warning 暗了 19 个色阶。
已回滚。

**改用语义令牌**，值保持原样：

| 令牌 | 值 | 用途 |
|---|---|---|
| `--dlg-danger-text` | `#f0a1a5` | 错误正文（最亮一档） |
| `--dlg-danger-text-soft` | `#edb9bb` | 错误说明，比正文淡 |
| `--dlg-danger-strong` | `#e88b8f` | 描边危险按钮字色 |
| `--dlg-danger-muted` | `#f0b9b2` | 危险状态徽章 |
| `--dlg-danger-warm` | `#f2b8b5` | 警示框正文 |
| `--dlg-danger-calm` | `#d9b4b4` | 大段警示（低饱和） |

**证据自证**：before/after 两张 PNG **大小完全相同（8967 字节）**，逐像素一致——
证明这次是纯重构，视觉零变化。若两张图不同，说明我把颜色改跑偏了。

## 10 · D 族实现：外发确认补上二次确认（`egress-confirm-before/after.png`）

按 `prototype-egress-confirm-family.html` 实现 AI 粗剪 / AI 修改两个弹窗的确认页。

### 改造前的实测对比

| 项 | 改前 | 改后 |
|---|---|---|
| 元数据 | 8 项**平铺**在同一 dl（目标/模型/字段/段落/Token/费用/哈希/有效期） | 按「给谁 / 发什么 / 规模 / 费用 / 凭据 / 有效期」分组 |
| **勾选框** | **完全没有** | 紧贴内容预览，未勾选时主按钮禁用 |
| 主按钮 | 普通主色 | **danger 色**（不可逆外发，不是普通「下一步」） |
| 危险说明 | 无 | 「这不是匿名化」明确告知 |

### 为什么这是真缺口

外发是**不可逆动作**，却是全仓唯一没有二次确认的破坏性操作——
删除素材、删除 Provider、删除转录都有确认弹窗，而「把内容发给第三方模型」
只需要点一下按钮。且费用与隐私同时受影响。

### 实现说明

勾选状态是**前端本地状态**（`aiEgressConfirmed` / `patchEgressConfirmed`），
不改 IPC 契约——Core 侧已有的 `egress_consent` 是服务端记录，这里是 UI 层的防误点。

### 过程中测试抓到我一次错误

我顺手把 AI 修改确认页的「上方指令来自当前本地输入；Core 确认 DTO 不包含正文」
从安全类 `readonly-note`（色块）改成了 `--plain`（中性小字）——
**把一条安全提示降级了**。是上一轮自己写的 `note-tiering.test.ts` 抓到的
（报「安全类应为 14 处，实际 13」）。已恢复为色块。

### 测试同步

3 处测试流程补上勾选步骤，并在其中一处**断言未勾选时按钮禁用**——
这条断言比"能点通"更有价值，它锁住了二次确认本身。
