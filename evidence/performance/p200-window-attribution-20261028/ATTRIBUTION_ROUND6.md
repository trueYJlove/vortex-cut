# P200 第六轮：立项判据本身被推翻（2026-10-28）

> 状态源一律引用 `docs/STATUS.md` §4 **P200**；本文只记录分析事实，不声明工程状态。
> **本轮零成本**：完全基于已入库的 `app-drop-p196-*.json`，未跑任何新测量。

## 0. 结论先说（按证据等级标注）

> 本文只用三级口径，见文末 §8。**否证只买到「摘掉假说」，不附带授予新假说的资格**。

- **【观测】** 那次 A/B 的对照组只覆盖 **40.6s**（`reached_end=true`），
  而冻结首次出现在**墙钟 53.6s / 时间码 48.4s**。
- **【成立·仅此一句】** ⇒ **该 A/B 不构成「时间线长度驱动」的证据**（对照组未进入冻结区间）。
  它**不能**推出「长度无关」，也**不能**推出任何替代成因。
- **【观测】** 真实现象不是「变慢」而是**近乎停摆**：段4–7 compose 间隔中位数 **2002ms**
  （0.42–0.45 帧/秒），段8 一度自行回升到 **5.32 帧/秒**。
- **【未定】** **触发量未点名**。现有证据里没有任何数字区分
  「累计播放时长 / 累计解码帧数 / 驻留水位 / 一次性事件」。本轮**不下成因结论**。

## 1. 关于上一轮（第五轮）的两处更正

第五轮把主因改判为「暂存帧被自身容量驱逐」，本轮复算发现该表述**两处不准**，
已同步修正 `docs/STATUS.md`：

### 1.1 命中率分母用错（4.4% → 27.9%）

第五轮写 `take_hit_exact/output` = 4.4%。但 `output` 是**解码器每吐一帧**的 trace
（`decode-worker.worker.ts:520-522`，`resDecoded += 1` 后立即 `trace("output")`），
冷启重解时每帧都会吐，**它不是客户端请求数**。

正确分母是 `enqueue`（客户端请求，`:1370`）= 22,976：

| 口径 | 长跑组 | 对照组 |
|---|---|---|
| `take_hit_exact / output`（**错**，第五轮用的） | 4.4% | 23.0% |
| `take_hit_exact / enqueue`（**对**） | **27.9%** | **79.0%** |

差距从 5× 修正为 2.8×。方向（长跑组命中率显著更低）不变，但量级被高估了。

### 1.2 驱逐与冷启的因果方向未定（原写「主因」过强）

`evict_stale` = 113,176。而按「cold_start × 平均 rebuildCost」估算：

```
1808 × 98.2（20 条采样的 mean(target − keyTarget)）= 177,455
实测 evict_stale = 113,176   ⇒ 比值 0.64
```

即**大部分驱逐可由冷启重解自身解释**（重解 n 帧则 n 帧进 stash 又几乎全被驱逐）。
故 `evict_stale` 至少部分是**冷启的后果**，不能单独当作「驱逐导致冷启」的证据。

真正无歧义的单向证据只有 `budget_raise_evicted_miss`（产品在驱逐后判 `missingStuck`
时才计数）= 1,384 / 1,808 = 76.5%，但它**只覆盖 76.5% 的冷启**，其余 23.5% 未归因。

## 2. 立项判据的致命缺陷：对照组没覆盖冻结时刻

| | 对照组 | 长跑组 |
|---|---|---|
| fixture | `5月11日(3)-1.mp4` | `p196-max21.mp4`（**同一素材** `-stream_loop 20`） |
| 覆盖时长 | **40.6s** | 926s |
| `reached_end` | `true` | `false` |
| 首次 ≥1s 冻结 | **无（最大间隔 51ms）** | **墙钟 53.6s / 时间码 48.4s** |

**对照组在 40.6s 就播完了，而冻结首次出现在 53.6s。** 一个在事件发生前就结束的对照，
不能证明短时间线免疫——它**没有进入冻结发生的区间**。

这是本条唯一的论据，且不需要更多论据（此前版本在这里还写了「两组素材不同」，
**该说法是错的**：P196 §2 记载长跑组夹具由**同一素材** `-stream_loop 20` 无损拼接、
逐字节同参。自相矛盾（同一句又说「同一素材重复 21 遍」）已删除）。

⇒ **结论仅限：这个 A/B 不构成「长度驱动」的证据。** 它**不能**推出长度无关。

**关于「那是什么驱动」——本轮不下结论。** 长跑组内部观察（第 1 遍零冻结、第 2 遍在
48.4s 冻结）与「累计状态」**相容**，但也与「该视窗内发生了某个一次性事件」相容；
本轮**没有任何数字**把触发量点名到「累计播放时长 / 累计解码帧数 / 驻留水位」之一。

## 3. 真实现象：不是变慢，是近乎停摆（且会自行回升）

按 `compose` 事件间隔把 926s 十等分（帧/秒）：

| 段 | 帧/秒 | 段 | 帧/秒 |
|---|---|---|---|
| 0 | 24.75 | 5 | **0.45** |
| 1 | 24.88 | 6 | **0.42** |
| 2 | 26.05 | 7 | **0.44** |
| 3 | 7.12 | 8 | **5.32** ← 自行回升 |
| 4 | **0.45** | 9 | **0.37** |

段4–7 的 compose 间隔**中位数 = 2002ms**（每 2 秒合成 1 帧）。

两个要点：

- **前 3 段是健康的**（24–26 帧/秒 ≈ 正常播放），这不是「长时线从头就慢」。
- **段8 回升到 5.32 帧/秒** ⇒ **排除「单调的资源线性耗尽」**（若是单调耗尽，不应回升）。
  但这只排除一类解释，**不确立**任何具体机制。

## 8. 证据等级（本文的口径约定）

第五轮与第六轮的反复，根因不是观测出错（数字都可复现、代码都如所述），
而是**每次都用错的置信度发布**。故自本轮起，本文只用三级：

| 级 | 含义 | 发布门槛 |
|---|---|---|
| **观测** | 某个数、某段区间、某个计数器、某行代码 | 复现命令能跑出同一数字 |
| **相容** | 与某假说一致 | **必须点名「还有什么也能产出同一信号」** |
| **成立** | 某假说已确立 | **必须点名「哪个检查能杀死它」，且该检查已做** |

**硬规则**：在同一份文档里否证甲的同时，**不得晋升乙**。

### 本文按该口径的重新归类

| 断言 | 等级 |
|---|---|
| 对照组覆盖 40.6s、`reached_end=true` | 观测 |
| 冻结首次出现于墙钟 53.6s / 时间码 48.4s | 观测 |
| ⇒ 该 A/B 不构成「长度驱动」的证据 | **成立**（算术：对照未进入事件区间） |

### 第五轮为什么会被推翻（诚实归因）

第五轮**否证重锚链的部分是合格的**（零基线、分布对比、代码路径三条独立）。
错在**同一份文档里顺手晋升了「驱逐是主因」**——而驱逐与冷启互为因果，
只凭 82.4% 的比值无法定向。补算那次乘法的成本是一次除法，我在第六轮才做。


时间码佐证：全程推进 489s，墙钟 929s，**比例 0.526**——播放速度只有实时的一半，
且 `dropped` 从 4 累计到 6,086。

## 4. 比原结论更严重的未登记事实：2/3 的请求拿到错帧

`near_repeat_substitute` = **15,181 = 66.1% 的 enqueue**。

该路径（`decode-worker.worker.ts:855-880`，`NEAR_REPEAT_RANKS = 3`）在目标帧被判
`missingStuck`/`behindCursor` 时，用**手里最近的帧**（相差 ≤3 个展示序位）顶替交付。
对照组无该计数。

⇒ 长跑组**约 2/3 的客户端请求拿到的是相邻帧而非目标帧**。
这修正了 P196「是慢不是坏」的判断：不是解不出，而是**在被顶替**。

（顶替本身只差 ≤3 帧，单次不解释 2–11s 冻结；它与冻结是两个并存现象，
本轮**不主张**二者有因果关系。）

## 5. 本轮边界（不得越读）

- 仍然只有**一次**长跑、单机、单素材（41s 连拼）。无多次运行方差。
- **未证明**冻结由哪个具体状态量触发（段8 回升说明不是单调耗尽，但也未定位）。
- **未证明**提高 `readyByPtsMax`/`unclosedBudget` 能消除停摆——第五轮曾把它列为
  下一轮方向，本轮的证据**不足以支持该方向优先于其他**。
- `output_p50` 1.9ms → 45.6ms 的成因仍未解释，与本轮结论正交。
- 20 条 `coldStarts` 是 1,808 次冷启的**样本**（`p33-user-drop` 取前 20 条），
  不是全集；其分布不代表全体。

## 6. 对下一步的影响

「造 ≥869s 夹具再跑一遍」这个动作**不再有明确的判别价值**——因为：

1. 冻结与「时间线长度」的因果关系未成立（§2），跑更长的线不一定能复现；
2. 现有一次运行已能复现，缺的不是长度而是**重复性与触发条件定位**；
3. `p200-reanchor-correlation` 的判据已在第五轮修正（带零基线），
   但它测的是「重锚相关性」，而重锚因果已被第五轮否证。

**建议的下一步**：用现有 `.tmp/p200/p200-long.mp4`（165.6s，不必再造）跑**多次**，
先在**短时长上复现停摆**（若 48s 附近必现，则 165s 夹具足够），把触发条件定位到
「累计播放时长 / 累计解码帧数 / 驻留水位」三者之一，再谈修法。
