# P196 跨窗播放无周期性卡顿 —— 实测记录（2026-10-27）

> 状态源一律引用 `docs/STATUS.md`；本文只记录**一次实测的事实**，不声明工程状态。

## 0. 结论先说

**门的原文要求在现有产品约束下不可执行**，实测在**可达上限（约 14.5 分钟时间线）**完成，
并且**不通过**：残余丢帧 24.0%（门限 0.5%）。丢帧**不是**周期性的窗口边界卡顿，
而是与「窗口取数延迟」同步的集中暂停（每约 10s 一次，每次 2–11s 画面冻结）。

## 1. 为什么不是 30 分钟

`services/core/src/aivs_core/rendering/ir.py:26`：

```python
MAX_IR_FRAMES = 27_000  # 15 分钟 @30fps（O2 体量护栏）
```

`ir.py:530-534` 对 `total_frames > MAX_IR_FRAMES` 直接抛 `PREVIEW_IR_TOO_LARGE`，
App 侧映射为「时间线超出实时合成预览的长度上限（约 15 分钟），已回退交互预览」
（`apps/desktop/src/app/preview/fallback-notice.ts:10`）。**该常量无环境变量覆盖**。

- 30 分钟 @30fps = 54000 帧 ⇒ 必然被拒，实时合成预览直接回退交互预览，
  根本进不了「跨窗播放」路径。实测证据：用 31.05 分钟夹具冒烟，预览面板出现
  回退提示「时间线超出实时合成预览的长度上限（约 15 分钟）」，`.synthetic-metrics` 永不出现。
- 打开该护栏属于改 `services/core`（本次任务禁止改动），且是既有体量护栏而非可调参数；
  越过它需要另立任务并做内存/驻留预算重评估。

因此本次跑的是**可达上限**：869.42s 时间线（26069 帧 ≤ 27000），14.49 分钟。

## 3. 判据（先声明，后看数）

复用仓库既有门 + 补一条周期性判据：

- **C1 丢帧率**（沿用 spec 既有的 `DROP_RATE_LIMIT`）：`dropped_frames / expected_frames ≤ 0.5%`。
- **C2 周期性**：若卡顿由「窗口边界」驱动，且窗口 = 300 帧 / 30fps = **10.0s** 时间线，
  则丢帧应集中在 `tc_us mod 10s` 的边界带内。判据：
  **边界带（±1s）每秒平均丢帧 / 其余时段每秒平均丢帧 ≥ 2.0** 判为「周期性卡顿」；
  **< 2.0** 判为「非边界驱动」。
- **C3 窗口取数**（IPC + JSON parse 侧，门明确要求不得遗漏）：
  **`window_fetch` p95 ≤ 500ms**（远低于一帧预算的 15 倍仍属可用；超过即会拖垮顺播）。
  另记 `window_fetch` 成功/失配/失败分类。
- **C4 合成长间隔**：`compose` 相邻间隔 `≥1000ms` 的次数 **= 0**（任何 1s 级画面冻结都算卡顿）。

预注册的补充口径（诚实性）：本次播放**未到片尾**（`reached_end=false`），只播了
时间线前 **488.2s / 869.4s（56.2%）**。因此：
**结果对「前 8.1 分钟成立」，不能外推到整条 14.5 分钟，更不能外推到 30 分钟。**

## 4. 实测

### 4.1 主跑（14.49 分钟时间线）

命令（实际执行，墙钟 965s ≈ 16.1 分钟）：

```
cd apps/desktop
AIVS_P33_MEDIA=<temp>/p196-max21.mp4 AIVS_P33_LABEL=p196-crosswindow-max \
AIVS_P33_DEADLINE_MIN=15 npx playwright test --config=tests/playwright.config.ts \
e2e/p33-user-drop.electron.spec.ts
```

| 指标 | 实测 | 判据 | 结论 |
|---|---|---|---|
| 丢帧 | **6086 / 26083 = 23.33%** | ≤0.5% | ❌ 超 47 倍 |
| 播放期丢帧（分母用实播 488.2s） | **4081 / 14647 = 27.9%** | — | 同上，更糟 |
| 边界带 / 其余 每秒均丢帧 | **7.76 / 8.07（比值 0.96）** | ≥2.0 才是周期性 | ✅ **不是窗口边界驱动** |
| `window_fetch` p50 / p95 / max | **2394 / 6592 / 10847 ms** | p95 ≤500ms | ❌ 超 13 倍 |
| `window_fetch` 结果分布 | 46 次全部 session=2（成功），0 失配 0 失败 | — | 不是错误，是**慢** |
| `compose` 间隔 p50 / p95 | 33.0 / 33.4 ms（≈30fps 正常） | — | 正常 |
| `compose` 间隔 ≥1000ms | **277 次** | =0 | ❌ |
| 播放进度 | 488.2s / 869.4s（56.2%），未到片尾 | 应跑满 | ⚠️ 见 §5 |
| 解码 p50 / p95 | 0.4 / 95.4 ms；分段 output_p95 245.6ms | — | 解码不是主因 |

49 个 10s 窗口周期里 **13 个零丢帧**、其余集中丢帧 —— 与「每约 10s 停在窗口边界等取数」
一致：`compose` 间隔 ≥1000ms 出现 277 次，而播放期约 49 个窗口，量级吻合。

**同一素材、同一 spec、同一台机器**：时间线从 41s 拉长到 14.5min，窗口取数从 24ms 涨到
2394ms，丢帧从 0 涨到 6086。这条 A/B 是本报告最硬的证据——退化**由时间线长度驱动**，
与「素材不同/机器不同/构建不同」无关。

## 5. 判定

- **C1 丢帧率：不通过**（23.33% vs 0.5%）。
- **C2 周期性：不是「窗口边界周期卡顿」**，但**存在明显的长周期卡顿**（每约 10s 一次、
  持续 2–11s 的画面冻结）。按要求「周期性」的负面结论成立，整体「无卡顿」**不成立**。
- **C3 窗口取数：不通过**（p95 6592ms vs 500ms）。
- **C4 合成长间隔：不通过**（277 次 ≥1000ms）。

**综上：门「跨窗播放无周期性卡顿」在可达上限（14.49 分钟）上判定不通过。**

## 6. 这次**没有**证明的（明确列出）

1. **没有**跑满 30 分钟——产品硬护栏 27000 帧（15 分钟）不允许，见 §1。
2. **没有**跑满 14.49 分钟全片——只播到 488.2s（56.2%），因丢帧导致播放推进慢于墙钟。
   所以 8.1 分钟之后的窗口行为未观测。
3. **没有**定位 `window_fetch` 慢在 IPC 传输、主进程取数、还是 renderer 侧 JSON 反序列化
   ——本证据只能证明「端到端窗口取数」慢，**不能**拆分归因。
   （回归 `window_fetch` ~ `start_frame`：斜率 0.18ms/帧、r=0.31，相关性弱到不能宣称 O(n)；
   但首窗 3087ms、末窗 10847ms，3.5x 增长是实测事实。）
4. **没有**证明这是回归还是**长时线从未成立**——仓库里没有更早的长时线基线可对账
   （既有证据全部是 41s 素材）。
5. **没有**覆盖「30 分钟里跨素材/跨 input 切换」——夹具是单素材无损循环。
6. **没有**测 v1（`VITE_AIVS_PREVIEW_IR_V2=0`）对照——本次是 v2 默认开启路径。
7. 单次运行，无重复测量；`variance` 未评估。

## 7. 观测到的附带问题（不属于本门，但值得登记）

`preview-session.ts:615-628` 的「B13-R R3 解码驻留预警」把**不阻断的提示**写进了
`session.lastError`，而 `SyntheticPreview.tsx:518-522` 在 `last_error` 存在时
**只渲染错误串、不再渲染指标行**。长时线必然触发该预警（本次 26083 帧 ⇒ 预计 15.3 GiB），
于是**指标条在长时线上永远显示一条预警文字**。且该预测是 v1 全量帧经验律，在 v2
窗口化帧源下已知不成立（原文自己写着「平台化不持续增长」）。本次 spec 因此改为
直接读 `window.__aivsPreviewMetrics` 判就绪，并把该前缀与真实错误区分开。
